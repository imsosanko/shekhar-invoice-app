# Shekhar Compute Tech Services — Invoicing App

A full invoicing/billing admin panel built as a real client/server application:

- **Backend:** Node.js + Express REST API, JWT-authenticated, with a simple JSON-file datastore (no native database compilation required).
- **Frontend:** Vanilla JavaScript, HTML, and CSS — no framework, no build step.
- **Python:** Two standalone scripts, invoked by the Node backend via `child_process`, generate the real invoice PDF (ReportLab) and Excel export (openpyxl).

```
shekhar-invoice-app/
├── server/
│   ├── server.js              # Express app entry point
│   ├── db.js                  # JSON-file datastore
│   ├── utils.js                # GST calculation, amount-in-words, currency formatting
│   ├── middleware/auth.js      # JWT auth middleware
│   ├── routes/                 # One file per resource (auth, customers, products,
│   │                           #   invoices, payments, expenses, settings, reports)
│   └── python/
│       ├── generate_pdf.py     # Builds the invoice PDF (ReportLab)
│       ├── export_excel.py     # Builds the invoice Excel export (openpyxl)
│       └── fonts/               # Bundled DejaVu Sans (so ₹ renders correctly everywhere)
├── public/                     # Static frontend served by Express
│   ├── index.html
│   ├── css/styles.css
│   └── js/
│       ├── api.js              # fetch() wrapper + JWT handling
│       └── app.js              # All page logic (dashboard, invoices, customers, etc.)
├── data/db.json                 # Created automatically on first run — your data lives here
├── package.json
├── requirements.txt
└── .env.example
```

## 1. Prerequisites

- **Node.js** 18 or newer
- **Python** 3.9 or newer, with `pip`

## 2. Install dependencies

```bash
# from the project root
npm install
pip install -r requirements.txt        # or: pip3 install -r requirements.txt --break-system-packages
```

If your system's Python binary is called something other than `python3` (e.g. plain `python` on some Windows setups), set `PYTHON_BIN` in a `.env` file — see `.env.example`.

## 3. Run it

```bash
npm start
```

Then open **http://localhost:3000**.

On the very first run, the server:
- seeds demo customers, products, and invoices so the app isn't empty,
- creates the admin login and **prints it once to the console**:

```
  First run: admin login created.
  Email:    sshashank1997@gmail.com
  Password: admin123  (change this in Profile → Security after signing in)
```

Change the password immediately after your first login from **Profile → Security**.

For development with auto-restart on file changes:
```bash
npm run dev
```

## 4. Configuration (optional)

Copy `.env.example` to `.env` to override defaults:

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `3000` | Port the server listens on |
| `JWT_SECRET` | a dev placeholder | **Set this to a long random string in production** |

## 5. What's real vs. what to know

- **Every number is computed server-side.** The browser shows a live preview total while you build an invoice, but the authoritative subtotal/item discounts/additional discount/CGST/SGST/IGST/grand total are calculated and stored by the Express API (`server/utils.js`) when you save.
- **Discounts** work at both levels: per line item (percentage or flat ₹) and an overall invoice-level discount (also percentage or flat ₹), applied after item discounts and allocated proportionally across items before tax so GST stays correct even with mixed tax rates.
- **PDF and Excel are real files**, generated by the two Python scripts, not client-side tricks.
- **5 invoice designs** (Modern Blue, Minimal Professional, Classic Business, Bold Header, Compact) are real, distinct PDF layouts in `server/python/generate_pdf.py` — not just cosmetic labels. Pick one in Settings → Invoice Design to set it as the default; override it per-download from the PDF preview toolbar.
- **4×6 Thermal format**: every invoice can also be generated as a compact 4×6 inch PDF suited to label/receipt printers (e.g. Rollo/Zebra-style), toggled from Settings (as the default) or the preview toolbar (per download). It always uses one dense layout regardless of which of the 5 designs is selected — there isn't room on a 4×6 label for five different designs.
- **Data storage** is a single JSON file (`data/db.json`) rather than a SQL database, hardened with atomic writes (write-to-temp-then-rename) and a rolling backup (`data/db.backup.json`) so a crash or power loss mid-write can't corrupt your data — the app automatically recovers from the backup if `db.json` is ever unreadable, and keeps the broken file as `db.json.corrupt` for inspection when even the backup fails. Every route only talks to `server/db.js`, so swapping in SQLite/Postgres later means rewriting one file, not the routes.
- **Auth** is JWT-based with bcrypt-hashed passwords, but there's only a single admin account by design (matching the original single-user admin-panel brief).
- **Offline sync** (see dedicated section below) — genuinely useful but deliberately scoped for reliability rather than trying to solve full offline-first conflict resolution.
- The **logo and UPI QR code** are stored as base64 inside `data/db.json` (fine for small images; very large/frequent uploads would be better served by on-disk file storage).

## 6. Offline sync

The app works with an unreliable or dropped connection, within a deliberate scope:

- **The app shell loads offline.** A service worker (`public/sw.js`) caches the HTML/CSS/JS, so opening the app with no connection still shows the UI instead of a browser error page.
- **Viewing data works offline.** Every successful GET response (dashboard, invoices, customers, etc.) is cached in the browser's IndexedDB. If a request fails because you're offline, the last-known data is shown instead, with a clear "You're offline — showing data cached from [time]" banner.
- **Editing existing records works offline.** Updating a customer/product/expense, changing settings, recording a payment, or editing an existing invoice — these are queued locally (IndexedDB outbox) if the network is down, and automatically replayed **in order** the moment connectivity returns. The top bar shows an "Offline — N changes pending" / "Syncing…" indicator the whole time.
- **Creating new records requires a connection**, on purpose. Invoice numbers and record IDs are assigned by the server (`server/db.js`), so a "Create" while offline can't be safely queued without risking duplicate/ colliding IDs once several offline devices reconnect. Attempting it shows a clear message rather than silently failing or creating something that later needs to be reconciled.
- This is a single-admin tool, so conflict resolution is intentionally simple: queued edits replay in the order they were made, last write wins. There's no multi-user merge logic.

## 7. Windows / Mac / Linux desktop app (fully offline)

This same app also runs as a native desktop application — no browser tab, no
internet connection required at all (fonts were switched from a Google Fonts
CDN to native OS fonts specifically for this). It's built with Electron,
wrapping the exact same Express server and Python scripts described above —
nothing was rewritten, so everything already documented in this README
still applies.

**What's different from the web version:**
- Runs in its own native window with a real File/View/Help menu, not a browser tab.
- Data is stored in the OS's proper per-user app-data folder (e.g. `%APPDATA%\shekhar-invoice-app\data\db.json` on Windows) instead of next to the app files, since an installed app's own folder may not be writable.
- The server picks its own free port automatically (starting near 51837) instead of always using 3000, so it can't conflict with anything else on your machine.
- If Python (or the `reportlab`/`openpyxl` packages) can't be found, the app shows a clear dialog explaining how to fix it instead of just failing silently — everything except PDF/Excel generation works fine either way.

### Running it in development

```bash
npm install
npm run electron
```

### Building the installer yourself

Pre-built Windows executables are provided alongside this project, but if you want to build them yourself (e.g. after making changes):

```bash
npm install
npm run dist:win            # builds both the installer and the portable .exe
npm run dist:win:portable   # portable .exe only
```

Output goes to `dist-installer/`. Building Windows executables from Linux/macOS requires Wine (`apt install wine` on Debian/Ubuntu) — building directly on Windows doesn't need anything extra. `npm run dist:mac` / `npm run dist:linux` build for those platforms respectively.

### Windows Python requirement

The desktop app still needs Python 3 with `reportlab` and `openpyxl` installed on the machine it runs on, for the same reason the web version does — PDF and Excel generation genuinely run through Python, not a JavaScript re-implementation. On first launch, if it can't find a working Python, it tells you exactly what's missing and offers to open python.org. To set it up:

1. Install Python 3 from python.org — check **"Add python.exe to PATH"** during setup
2. Open Command Prompt and run: `pip install reportlab openpyxl`
3. Launch (or restart) the app

Everything else — invoices, customers, dashboard, reports — works with no Python installed at all; only PDF/Excel generation needs it.

### What I actually verified for the desktop build (not just assumed)

- Installed and ran real Electron in this environment, confirmed the compiled server starts correctly on a dynamically-chosen free port, and screenshotted the actual running native window — the real login screen renders correctly, fully offline.
- Confirmed data is written to the correct OS user-data directory (not the app bundle) by inspecting the filesystem after a run.
- Built the real Windows executables (both the NSIS installer and the portable single-file .exe) end-to-end using Wine, and verified with `file` that both are genuine Windows PE32 GUI executables.
- Found and fixed a real packaging bug in the process: when bundled into Electron's `.asar` archive, the path to the Python scripts pointed *inside* that virtual archive, which an external Python process can't read from. Fixed by resolving to the sibling `app.asar.unpacked` folder (where `asarUnpack` in `package.json` actually places those files on disk), and confirmed the corrected path resolves correctly before rebuilding.

## 8. Deploying online

**Netlify cannot run this app**, and it's worth explaining exactly why rather than fighting it halfway through a deploy: per [Netlify's own docs](https://docs.netlify.com/functions/build/), Netlify Functions only support JavaScript, TypeScript, and Go — there's no Python runtime at all, which this app's PDF/Excel generation genuinely needs. On top of that, Netlify has no persistent server (this is a real Express app, not a handful of serverless functions) and no persistent filesystem (the JSON database would be wiped constantly). None of that is a code problem to fix — it's a mismatch between what this app is and what Netlify hosts.

### Recommended: Render, Railway, or Fly.io (Docker)

These all run a real container with both Node and Python, which is exactly what this app needs — the included `Dockerfile` works on any of them unchanged. Render is the easiest to get started with:

1. Push this project to a GitHub repo.
2. In Render: **New +** → **Blueprint**, point it at the repo (it reads `render.yaml` automatically) — or **New +** → **Web Service** → choose **Docker** as the runtime if you'd rather configure it by hand.
3. Before or right after the first deploy, set real values for `JWT_SECRET` and `ADMIN_DEFAULT_PASSWORD` (`render.yaml` generates a random `JWT_SECRET` for you automatically, and defaults the admin password to `admin123` — change that).
4. `render.yaml` attaches a **persistent disk** at `/app/data`. This matters: without it, `data/db.json` lives on the container's throwaway filesystem and every redeploy or restart silently erases all your invoices/customers. Railway and Fly.io both offer the equivalent (a "volume") — attach one at the same path if you deploy there instead.
5. Once deployed, your app is live at the URL Render gives you — same login flow, same everything, as running it locally.

I verified every command in the Dockerfile against this exact project — `npm install --omit=dev` (confirms Electron, a devDependency, is correctly excluded — the image doesn't need the ~200MB desktop-app runtime), `pip3 install --break-system-packages -r requirements.txt`, and booting the server with the same environment variables and data directory the container will use — all tested and working. I could not run `docker build` itself in the sandbox this was built in (no Docker available there), so the image has not been build-tested end-to-end; if anything doesn't work, it's most likely a small base-image quirk, not the app logic, which is otherwise identical to the already-extensively-tested local version.

### If you specifically want Netlify involved

The one legitimate way to use Netlify here is a **hybrid deploy**: host only the static frontend (`public/`) on Netlify's CDN, while the real backend runs on Render (above). Included `netlify.toml` does this by proxying `/api/*` requests through to your Render URL, so the frontend's existing `fetch('/api/...')` calls work completely unchanged — no code edits, no CORS setup, because from the browser everything still appears to come from your Netlify domain.

1. Deploy the backend to Render first (above) and note its URL.
2. Edit `netlify.toml` and replace `YOUR-BACKEND-URL` with that Render URL (two places).
3. In Netlify: **Add new site** → point it at this repo — it reads `netlify.toml` automatically (publish directory `public`).

This genuinely works, but it's strictly more moving parts than just deploying the whole thing to Render — worth doing only if you specifically want Netlify's CDN/edge network in front of the static assets.

### Before going live with real users

- Change `JWT_SECRET` to a long random value and `ADMIN_DEFAULT_PASSWORD` away from the default — this now faces the internet, not just your own machine.
- This is still a **single-admin app by design** (one login, matching the original brief) — it works fine as your own private tool online, but wasn't built for multiple independent businesses to sign up and use it.
- The offline-sync feature (section 6) is far less relevant once the app has a stable internet connection to a real host — it's mainly there for the desktop app and shaky local connections.

## 9. Tested end-to-end

Every feature in this README was actually exercised against a running server during development, not just written and assumed to work — including: login and JWT-protected routes; full CRUD on customers/products/expenses; invoice creation with server-computed GST (same-state CGST/SGST, inter-state IGST, and Non-GST); item-level and invoice-level discounts (percentage and flat, together, allocated correctly before tax); payment recording that auto-marks invoices Paid; dashboard/report aggregation; all 5 PDF designs plus the 4×6 thermal format (visually reviewed as rendered images, not just "it returned 200"); Excel export; and database corruption recovery via the automatic backup.

Two real bugs were found and fixed this way rather than shipped: the ₹ symbol not rendering in PDFs (missing Unicode font), and a flat-₹ item discount being misread as a percentage in the PDF's line-item amount column.
